Go Backend

TollMeshCache core is built in Go with CRDTs for distributed coordination.

Core Components

GCounter (Grow-only Counter)

Used for distributed rate limiting. Each node maintains its own count; the total is the sum of all node counts.

counter := core.NewGCounter("node-1")
counter.Increment(5)
total := counter.Value()

GSet (Grow-only Set)

Used for replay protection. Distributed set of seen nonces that automatically converges across nodes.

set := core.NewGSet()
set.Add("nonce-123")
exists := set.Contains("nonce-123")

API Operations

Consume: Rate limiting

result, err := meshStore.Consume(ctx, key, limit, window)

Seen: Replay protection

seen, err := meshStore.Seen(ctx, key, ttl)

Get/Set: Caching

meshStore.Set(ctx, namespace, key, value, ttl)
value, exists, err := meshStore.Get(ctx, namespace, key)

Python SDK

Async/sync Python client with type hints and retry logic.

Installation

pip install tollmeshcache
pip install tollmeshcache[async]  # For async support

Quick Start

from tollmeshcache import Client, AsyncClient, ClientConfig
from datetime import timedelta

# Sync client
config = ClientConfig(host='localhost', port=8080)
client = Client(config)

result = client.consume('user-123', 100, timedelta(minutes=1))
if result['ok']:
    print('Request allowed')

# Async client
async with AsyncClient(config) as client:
    result = await client.consume('user-123', 100, timedelta(minutes=1))

Rust SDK

Full async/await with tokio and type-safe error handling.

Installation

[dependencies]
tollmeshcache = "1.0"
tokio = { version = "1", features = ["full"] }

Quick Start

use tollmeshcache::{Client, ClientConfig};
use std::time::Duration;

#[tokio::main]
async fn main() -> Result<(), Box> {
  let config = ClientConfig::new()
    .with_host("localhost")
    .with_port(8080);

  let client = Client::new(config)?;

  // Rate limiting
  let result = client.consume("user-123", 100, Duration::from_secs(60)).await?;
  if result.ok {
    println!("Request allowed");
  }

  Ok(())
}

API Reference

Complete API documentation for all SDKs.

Core Operations

1. consume(key, limit, window) - Rate Limiting

Consume tokens from a distributed rate limiter.

Parameters:
- key (string): Rate limit bucket key
- limit (integer): Maximum tokens in window
- window (duration): Time window

Returns: {ok, remaining, reset_at}

2. seen(key, ttl) - Replay Protection

Check if a nonce has been seen before.

Parameters:
- key (string): Nonce or request ID
- ttl (duration): Memory duration

Returns: {seen: boolean}

3. cache_set(namespace, key, value, ttl) - Cache Storage

Store a value in the distributed cache.

4. cache_get(namespace, key) - Cache Retrieval

Retrieve a value from the distributed cache.

5. health() - Health Check

Check cluster health and node status.

6. get_peers() - List Cluster Peers

Get list of connected cluster nodes.

TollMeshCache vs Redis

A detailed comparison for choosing the right solution.

Feature Comparison

Feature TollMeshCache Redis
Language Support ✅ 7 languages ⚠️ CLI-based
Rate Limiting ✅ Built-in ⚠️ Custom logic
Replay Protection ✅ Built-in ⚠️ Custom logic
No Central Server ✅ Peer-to-peer ❌ Single master
CRDT Convergence ✅ Automatic ⚠️ Requires Sentinel
Type Safety ✅ Native types ⚠️ String-based
Throughput ⚠️ 50k/node ✅ 100k+ ops

When to Use TollMeshCache

  • ✅ Distributed rate limiting without central server
  • ✅ Replay protection and nonce tracking
  • ✅ Edge computing and distributed caches
  • ✅ Microservices coordination
  • ✅ Zero-config deployment

When to Use Redis

  • ✅ High throughput (100k+ ops/sec)
  • ✅ Complex data structures (sorted sets, streams)
  • ✅ Pub/Sub messaging
  • ✅ Session management at scale
  • ✅ Real-time analytics
Best Practice: Use both! TollMeshCache for distributed rate limiting & replay protection, Redis for high-frequency caching & real-time features. They're complementary, not competitive.
